# 自治体のデータを作る手順書（エージェント用）

ごみ出しカレンダーに、新しい自治体（市区町村）を足すときの手順と決まりです。
エージェント（Claude など）は **県ごとに1つ** 決めて、その県の市町村を、この手順書のとおりに **1つずつ** 作ります（下の「0. 県ごとの進め方」）。
人（このアプリの持ち主）は、最後に「人がやること」を片づけて、できあがりを確かめてから公開します。

置き場所・道具のくわしい説明は [README.md](README.md)、毎年の更新は README.md の「毎年4月」を見てください。

---

## 0. 県ごとの進め方

1. **1つの県は、1つのエージェント（県の係）が受け持つ。** ほかの県の係と同時に動いてよい。同じ県を2つのエージェントで同時に作らない。
2. **はじめに県のメモを読む（なければ作る）**：`gomiappV3.1/tools/munis/<県>/県のメモ.md`（ひな形は `tools/munis/県のメモ_ひな形.md`）。
   県で共通のもの（県のオープンデータカタログ・e-Stat の地図・郵便番号一覧・県内の市でよくある資料の形・まねる元）と、市町村ごとの進み具合の表がある。
3. **作る順番**：人口の多い市から。メモの表に並べて、上から1つずつ作る。人に順番を言われたら、そのとおりにする。
4. **1つの自治体ごとに区切る**：「2. 作業の流れ」の 1〜13 を終えて、その自治体のファイルと県の地図（`geo/<県>.json`・`geo/index.json`・`data/…/towns.js`）をコミットし、県のメモの表を「できた」にして、短く報告してから次へ進む。
   - `data/municipalities.js`（全国で1つのファイル）は、自治体の1行を足すだけ。**県の係が同時に動いているときは、ここだけコミットしない**（メインがまとめてコミット。決まり D2）。1つの県の係だけが動いているときは、いっしょにコミットしてよい。
5. **止まったとき**：資料がない（決まり D4）・決まりにない判断が要る自治体は、メモの表を「保留」にして理由を書き、**次の自治体へ進む**。まとめて人に聞く。
6. **長くなったら交代してよい**：県のメモと各自治体の README.md に、次の係が続けられるだけのことを書いておく（どこまでできたか・次にやること）。
7. **県が終わったら**：メモの表がすべて「できた」か「保留（理由）」になったら、`status.py` で県の進み具合を見て、人に報告する（できた数・保留の一覧・人がやることのまとめ）。

**決まりの一覧（目次）**

| 分け方 | 決まり |
| --- | --- |
| A. データの中身 | A1 市の情報より詳しくしない／A2 番号と名前はコード表／A3 町名は市の書き方／A4 資料を探す順番 |
| B. 見た目と使いやすさ | B1 区分の色は市のカレンダーの色／B2 地区は探しやすく（検索用の町名）／B3 市が公表していない日は、使う人がえらぶ |
| C. 利用条件と公開 | C1 利用条件を license.json に／C2 公開してよいか（無料版・ストア版）／C3 照合用のデータは画面に出さない |
| D. 作業のしかた | D1 自分の県・自治体のファイルだけ／D2 県の係が同時に動くとき／D3 Push しない／D4 資料が見つからないとき／D5 データの大きさ |

## 1. 決まり（いちばん大事）

### A. データの中身

- **A1 自治体の情報より詳しくしない。** 地区・町名の分け方は、市の資料のとおりにする。細かく分けたり、まとめたりしない。
  - 市の資料に載っていない町は、アプリに足さない（状況一覧に「参考」で出るだけでよい）。
  - 収集日・品目・出し方は、市の資料に書いてあることだけ。推測で日付や品目を作らない。
  - 「今いる場所から探す」や地区の検索でも、町と地区の対応は市の資料（地区の一覧・人口統計の自治会の表など）で決める。近くの町から「たぶん」で決めない。
- **A2 自治体の番号と名前は、総務省の全国地方公共団体コードのとおり。**
  コード表：`元データ/全国/地方公共団体コード/lgcode.json`（なければ `python gomiappV3.1/tools/build_lgcode.py`）。
  - 政令指定都市は、市を1つの自治体にして、区は `city.js` の `regions`（地域）にする（例：京都市）。
- **A3 町名は市の資料の書き方。** 直してよいのは、正式な町名（郵便番号一覧 `元データ/全国/郵便番号/県別/`）と1字だけちがう、明らかな誤字・異体字だけ。直したら README.md に書く。
- **A4 資料はこの順に探す。** いちばん上で見つかったものを使う。
  1. 自治体のオープンデータ（自治体標準オープンデータセットの「ごみ収集日」「ごみ分別」、県のオープンデータカタログ。出典を書けば商用で使える）
  2. 市のホームページの PDF・ページ（収集カレンダー、地区の一覧、分別の一覧）
  3. 市の分別の冊子（PDF。画像だけなら画像を見て書き写す）

### B. 見た目と使いやすさ

- **B1 区分の色は、市の配布物の色に近づける。** 人は色で覚えるので、市のカレンダーを見ている人が、アプリでも同じ色で分かるようにする（ほかのアプリのように、自分で決めた色にしない）。
  - いちばん先に使うのは、**市のカレンダー**（毎日見るもの）の日付のマスや凡例の色。
  - カレンダーが白黒のときや、カレンダーにない区分は、市の冊子・ポスターの色。
  - どれにも色がないときだけ、ほかの区分と見分けやすい色を選ぶ。
  - 色は PDF から取り出す（マスの色を画像で見る）。うすい色・白い札は、`city.js` の `darkInk` に入れて文字を黒にする。
  - どの資料の何ページの色にしたかを README.md に書く。
- **B2 地区は、住んでいる人が自分で探せるようにする。**
  - アプリは、地区が15以上ある市には検索欄を出す（地区名・よみ・説明と、下の「検索用の町名」で探せる）。
  - 地区名が校区や自治会の名前で、町名から分からない市は、`geo.py` で町と地区を対応させる（決まり A1 のとおり、市の資料で）。
    `build_geo.py` が、その対応から **検索用の町名**（`data/<県>/<自治体>/towns.js`）を作る。町名で探すと「新天町 → 新川」のように出る。
  - 市の資料に、町名のほかに地区ごとの呼び名（通称・自治会の呼び名）があれば、`geo.py` の `search_words(cal)` で返すと、検索に足される（例：宇部市）。
  - 地区名がそのまま町名の市（京都市）は、`geo.py` に `TOWN_SEARCH = False` と書く（中身が空の towns.js になる）。

- **B3 市が町ごとの収集日を公表していない区分は、使う人がえらべるようにする。**（例：高知市の資源物・不燃ごみ「第1月曜日〜第4金曜日の20地区」）
  - 市が「えらべる日の種類」（例：第1月曜日〜第4金曜日）と、祝日・年末年始の変更（休日の収集計画など）を公表していれば、`calendar.py` で、えらべる日ごとの1年分の収集日を作り、`calendar.js` の `choice` に入れる（推測しない。変更の表がないときは作らずに人に相談）。
  - アプリは、地区の下に「○○の日をえらんでください」を出し、えらんだ日（第○○曜日）をカレンダー・つぎの収集日・品目の「次に出せる日」に出す。「わからない」もえらべる。
  - えらぶ日に出す区分がいくつもあるとき（紙類・カン・不燃…）は、カレンダー用の札を1つ作り（例：「資源物・不燃ごみ」）、`city.js` の `dayAs` で品目の区分をその札につなぐ。
  - 市が種類も公表していないときは、カレンダーに入れず、区分の説明に「収集日は町内会の回覧か市へ」と書く（決まり A1）。

### C. 利用条件と公開

- **C1 使った資料の利用条件を必ず `license.json` に書く。** 商用で使えるか（可・出典表示で可・要確認・要許可）と、許可の問い合わせ先。
- **C2 公開してよいか。**
  - 無料で公開している GitHub 版（ホームページ）には、市の資料を正しく写して出典を書けば出してよい（市のサイトの「リンク・引用」の範囲で使う）。
  - **ストア版（アプリストアで配る・広告をのせる）には、「商用利用」が「可」「出典表示で可」か、市の許可が取れた自治体だけを入れる。** 「要確認」「要許可」の自治体は、許可が取れるまで入れない。
  - 許可を頼むときは、問い合わせ文を `元データ/<県>/<自治体>/問い合わせ文.md` に作る（例：防府市・宇部市）。中身：①使いたい情報（収集日・地区・出し方）と使い方（無料・ストア・広告）②町と地区の対応の資料があるか ③ほかに聞きたいこと。名前と連絡先は〔　〕にして、人が書く。
  - 許可が取れたら、`license.json` の「許可の記録」に、日付・相手・条件（出典の書き方など）を書く。
- **C3 照合用のデータ（郵便番号一覧・e-Stat の町の境目）は、確かめるためだけに使う。** 郵便番号一覧の町名をアプリの画面に出さない（e-Stat の町名は、今いる場所・検索用の町名に使ってよい）。

### D. 作業のしかた

- **D1 自分の県・自治体のファイルだけ触る。** 触ってよいのは、受け持つ県の `data/<県>/`・`tools/munis/<県>/`・`元データ/<県>/`・`geo/<県>.json`。ほかの県・アプリ本体（index.html）・共通の道具は変えない。変える必要があれば「人がやること」に書く。
- **D2 並べて作業するとき（県の係が同時にいくつも動く）。**
  - 全国で1つのファイル（`data/municipalities.js`・`geo/index.json`）は、自治体の1行を足す・`build_geo.py <県コード>` を動かすところまで。**コミットはしない**。メイン（取りまとめる人・セッション）が、まとめてコミットする。README の「人がやること」に「共通ファイルはメインがコミット」と書く。
  - 県の地図（`geo/<県>.json`）は、その県の係だけが触るので、自分でコミットしてよい。
  - `build_geo.py` は、必ず自分の県のコードを付けて動かす（付けないと、ほかの県の地図も作り直してしまう）。
  - コミットは、自分のファイルだけを `git add <パス>` で足す（`git add -A`・`git add .` は使わない）。`index.lock` で失敗したら、少し待ってやり直す。
- **D3 Push しない。** コミットまで（ブランチを分けているときは、そのブランチに）。
- **D4 資料が見つからないとき（小さな町村など）。** 次のときは作らずに止めて、README.md と報告に「資料なし」と理由を書く（状況一覧では「作業中」のまま）。
  - 収集日がネットにない（紙だけ・回覧板だけ）、ログインや画像認証が要る、カレンダーが地区ごとに手書きで読めない。
  - 1年分の収集日がそろわない（例：4〜12月だけ）。そろうまで待つ。
  - 推測で埋めない（決まり A1）。人が市に問い合わせて資料をもらえたら、続きを作る。
- **D5 データの大きさ。** スマホが重くならないように、1つの自治体の `calendar.js` は **1MB まで**、`items.js` は 300KB までを目安にする。
  - こえそうなとき（地区が何千もある大きな市）は、同じ日程の地区をまとめる（`areas` は日程の名前を指すだけにする）。それでもこえるなら、人に相談する（区ごとに分けるなど、アプリを直す必要がある）。
  - 地図（`geo/<県>.json`）は県ごと。2MB をこえる県は人に相談する。

## 3. データの形

アプリが読むデータは3つ（`gomiappV3.1/data/<県>/<自治体>/`）。自分で書かず、道具（`calendar.py` など）で作る。

- **calendar.js**（収集日）：`{"year": 年度, "schedules": {日程: {"rules": {区分: "毎週月・木曜日"}, "days": {"2026-04-01": [区分, …]}, "moved": {}}}, "areas": [{"n": 地区名, "r": 地域, "s": 日程, "y": よみ, "d": 説明}]}`
  - 日付はその年度（4月1日〜3月31日）だけ。区分は city.js の `cats` の名前。
  - 曜日で決まる市も、1年分の日付にして入れる（年末年始の休みを抜く）。
- **items.js**（品目）：1行に1品目。`[品名, 区分, よみ, 注意]` か `{"n", "c", "y", "d"}`。
- **calendar.js の choice**（使う人がえらぶ収集日。決まり B3。なくてよい）：`{"label": "資源物・不燃ごみの日", "cat": カレンダーの札の区分, "rule": "毎月{o}（月1回）", "ask": えらぶときの文, "help": 説明, "options": {"第1月曜日": {"days": [日付…], "moved": [休日で変更した日付…]}, …}}`。
- **towns.js**（検索用の町名）：`{"t": [[町名, [地区の番号, …]], …]}`。地区の番号は calendar.js の `areas` の順番。`build_geo.py` が作るので、手で書かない。
- **city.js**（設定）：項目は [README.md](README.md) の「city.js の項目」。

### 人に渡すもの・記録の形式

| 用途 | 形式 | 理由 |
| --- | --- | --- |
| 手順書・作業報告・人がやること | **Markdown（.md）** | GitHub・エディタでそのまま読めて、変わったところが見やすい。エージェントも読み書きしやすい |
| プログラムが読むデータ・設定 | **JSON**（`license.json` など） | 項目が決まっていて、自動チェックできる |
| 一覧表（進み具合・コード表など人が Excel で見るもの） | **CSV（UTF-8・BOM 付き）** | Excel でそのまま開ける |
| 市の資料 | **元の形のまま（PDF・HTML・CSV）** を元データに保存 | 作り直し・見くらべに使う。PDF は資料として残すだけで、作業の記録には使わない |

## 4. できあがりの条件

次がすべてそろったら「できた」。そろわないものは README.md の「人がやること」に書いて、報告する。

1. `check_muni.py <コード>` で **直す 0**（注意は、理由を README.md に書けばよい）
2. `status.py` で、その自治体の行に **赤がない**
3. 地区の数が、市の資料の地区（町名）の数と合っている（ちがうときは理由を書く）
4. **収集日を市の資料と見くらべた**：日程（地区）を3つ以上えらび、それぞれ 4月・8月・12月〜1月（年末年始）・3月の日付を見くらべて、合っていた
5. 品目を10個以上えらんで、区分が市の資料と合っていた
6. 「今いる場所から探す」：地区が決まる町が 85% 以上（決まらない町は、山の中など理由を書く）
7. `license.json` に、使った資料がすべて書いてある
8. 区分の色が、市のカレンダー（なければ冊子・ポスター）の色に近い（決まり B1。どの資料の色かを README.md に書いた）
9. 地区が15以上ある市は、アプリの地区の検索欄で町名を入れると、その町の地区が出る（決まり B2。`towns.js` ができている）

## 5. 作業報告の形（README.md）

`gomiappV3.1/tools/munis/<県>/<自治体>/README.md` に、次の見出しで書く。

```markdown

- アプリのデータ：`gomiappV3.1/data/<県>/<自治体>/`
- 元データ：`元データ/<県コード>_<県名>/<コード>_<名前>/`
- 問い合わせ：<課の名前> <電話>

## 収集日
（使った資料と URL、読み取り方、毎年やること）

## 品目
（使った資料、件数、手で足したもの）

## 今いる場所から探す
（町名と地区の対応のしかた）

## 確かめたこと
- 自動チェック：直す 0・注意 <n>（<日付>）
- 収集日：<地区>の 4/○・8/○・12/○・1/○・3/○ を市のカレンダーと見くらべて合っていた …
- 品目：<品目>…の区分が市の一覧と合っていた
```

## 6. 毎年の更新

新しい年度の資料が出たら（ふつう2〜3月）、`download_sources.py` → `update_year.py` → `check_muni.py` → `status.py`。
曜日で決まる市は、年末年始の日程（10〜11月ごろ発表）だけを `calendar.py` の `YEAR_END` に足す。

**古い年度の元データ**：新しい年度のデータを公開して2か月たったら（その年度の6月から）、前の年度の `元データ/…/<年度>年度/` は消してよい（状況一覧に「消してよい古い年度」と出る）。
いつも残すのは今の年度と次の年度。冊子（`分別の冊子/`）・地図（`地図/`）・オープンデータ（`オープンデータ/`）は消さない。アプリの収集日は GitHub の履歴に残る。
