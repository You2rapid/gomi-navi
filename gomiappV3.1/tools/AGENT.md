# 自治体のデータを作る手順書（エージェント用）

ごみ出しカレンダーに、新しい自治体（市区町村）を1つ足すときの手順と決まりです。
エージェント（Claude など）は、この手順書のとおりに **1回の作業で1つの自治体** を作ります。
人（このアプリの持ち主）は、最後に「人がやること」を片づけて、できあがりを確かめてから公開します。

置き場所・道具のくわしい説明は [README.md](README.md)、毎年の更新は README.md の「毎年4月」を見てください。

---

## 1. 決まり（いちばん大事）

1. **自治体の情報より詳しくしない。** 地区・町名の分け方は、市の資料のとおりにする。細かく分けたり、まとめたりしない。
   - 市の資料に載っていない町は、アプリに足さない（状況一覧に「参考」で出るだけでよい）。
   - 収集日・品目・出し方は、市の資料に書いてあることだけ。推測で日付や品目を作らない。
2. **自治体の番号と名前は、総務省の全国地方公共団体コードのとおり。**
   コード表：`元データ/全国/地方公共団体コード/lgcode.json`（なければ `python gomiappV3.1/tools/build_lgcode.py`）。
   - 政令指定都市は、市を1つの自治体にして、区は `city.js` の `regions`（地域）にする（例：京都市）。
3. **町名は市の資料の書き方。** 直してよいのは、正式な町名（郵便番号一覧 `元データ/全国/郵便番号/県別/`）と1字だけちがう、明らかな誤字・異体字だけ。直したら README.md に書く。
4. **資料はこの順に探す。** いちばん上で見つかったものを使う。
   1. 自治体のオープンデータ（自治体標準オープンデータセットの「ごみ収集日」「ごみ分別」、県のオープンデータカタログ。出典を書けば商用で使える）
   2. 市のホームページの PDF・ページ（収集カレンダー、地区の一覧、分別の一覧）
   3. 市の分別の冊子（PDF。画像だけなら画像を見て書き写す）
5. **使った資料の利用条件を必ず `license.json` に書く。** 商用で使えるか（可・出典表示で可・要確認・要許可）と、許可の問い合わせ先。
6. **照合用のデータ（郵便番号一覧・e-Stat の町の境目）は、確かめるためだけに使う。** アプリの画面には出さない。
7. **自分の自治体のファイルだけ触る。** ほかの自治体・アプリ本体（index.html）・共通の道具は変えない。変える必要があれば「人がやること」に書く。
8. **Push しない。** コミットまで（ブランチを分けているときは、そのブランチに）。

## 2. 作業の流れ

コードは5けた（例：35215）、`<県>` は `35_yamaguchi`、`<自治体>` は `35215_shunan` のような形。

| # | やること | できるもの |
| --- | --- | --- |
| 1 | コード表で、コード・名前・よみ・種類（市・町・村・政令指定都市）を確かめる | － |
| 2 | 資料を探して、`元データ/<県コード>_<県名>/<コード>_<名前>/<年度>年度/` に保存する。冊子は `分別の冊子/`、地図は `地図/` | 元データ |
| 3 | `gomiappV3.1/data/municipalities.js` に1行足す（新しい県なら `prefs` にも） | 登録 |
| 4 | いちばん似ている自治体の道具をまねて `calendar.py` を作る（下の「まねる元」）。`python gomiappV3.1/tools/update_year.py <年度> <コード>` | `calendar.js` |
| 5 | 品目を作る（オープンデータなら `opendata.py`、なければ `make_items.py`） | `items.js` |
| 6 | `city.js` を作る（区分・色・袋・出し方・問い合わせ先・画面下の出典） | `city.js` |
| 7 | e-Stat の町丁・字の境界 KML を `地図/` に置き、`geo.py` を作って `python gomiappV3.1/tools/build_geo.py <県コード>` | `geo/<県>.json` |
| 8 | `license.json` を書く（ほかの自治体のものをまねる） | 商用利用の記録 |
| 9 | `README.md` を書く（下の「作業報告の形」） | 作業報告 |
| 10 | 自動チェック：`python gomiappV3.1/tools/check_muni.py <コード>` →「直す」を0にする | － |
| 11 | 状況一覧：`python gomiappV3.1/tools/status.py` → その自治体の行に赤がないこと | － |
| 12 | 市の資料と見くらべる（下の「できあがりの条件」の4〜6） | README の「確かめたこと」 |
| 13 | コミット（自分の自治体のファイルだけ）。報告に、自動チェックの結果（`--md`）と「人がやること」を書く | － |

### まねる元

| 市の資料の形 | まねる自治体 |
| --- | --- |
| 日程（A・B…）ごとのカレンダー PDF（色のついたマス） | 周南市 `35_yamaguchi/35215_shunan` |
| 地区ごとのカレンダー PDF（文字）・冊子を OCR | 光市 `35_yamaguchi/35210_hikari` |
| オープンデータの CSV（収集日・品目・地区の一覧） | 下松市 `35_yamaguchi/35207_kudamatsu` |
| 町ごとに曜日で決まる（毎年のカレンダーがない）・政令指定都市 | 京都市 `26_kyoto/26100_kyoto` |

## 3. データの形

アプリが読むデータは3つ（`gomiappV3.1/data/<県>/<自治体>/`）。自分で書かず、道具（`calendar.py` など）で作る。

- **calendar.js**（収集日）：`{"year": 年度, "schedules": {日程: {"rules": {区分: "毎週月・木曜日"}, "days": {"2026-04-01": [区分, …]}, "moved": {}}}, "areas": [{"n": 地区名, "r": 地域, "s": 日程, "y": よみ, "d": 説明}]}`
  - 日付はその年度（4月1日〜3月31日）だけ。区分は city.js の `cats` の名前。
  - 曜日で決まる市も、1年分の日付にして入れる（年末年始の休みを抜く）。
- **items.js**（品目）：1行に1品目。`[品名, 区分, よみ, 注意]` か `{"n", "c", "y", "d"}`。
- **city.js**（設定）：項目は [README.md](README.md) の「city.js の項目」。

### 人に渡すもの・記録の形式

| 用途 | 形式 | 理由 |
| --- | --- | --- |
| 手順書・作業報告・人がやること | **Markdown（.md）** | GitHub・エディタでそのまま読めて、変わったところが見やすい。エージェントも読み書きしやすい |
| プログラムが読むデータ・設定 | **JSON**（`license.json` など） | 項目が決まっていて、自動チェックできる |
| 一覧表（進み具合・コード表など人が Excel で見るもの） | **CSV（UTF-8・BOM 付き）** | Excel でそのまま開ける |
| 市の資料 | **元の形のまま（PDF・HTML・CSV）** を元データに保存 | 作り直し・見くらべに使う。PDF は資料として残すだけで、作業の記録には使わない |

## 4. できあがりの条件

次がすべてそろったら「できた」。そろわないものは README.md の「人がやること」に書いて、報告する。

1. `check_muni.py <コード>` で **直す 0**（注意は、理由を README.md に書けばよい）
2. `status.py` で、その自治体の行に **赤がない**
3. 地区の数が、市の資料の地区（町名）の数と合っている（ちがうときは理由を書く）
4. **収集日を市の資料と見くらべた**：日程（地区）を3つ以上えらび、それぞれ 4月・8月・12月〜1月（年末年始）・3月の日付を見くらべて、合っていた
5. 品目を10個以上えらんで、区分が市の資料と合っていた
6. 「今いる場所から探す」：地区が決まる町が 85% 以上（決まらない町は、山の中など理由を書く）
7. `license.json` に、使った資料がすべて書いてある

## 5. 作業報告の形（README.md）

`gomiappV3.1/tools/munis/<県>/<自治体>/README.md` に、次の見出しで書く。

```markdown
# <県名> <自治体名>（<コード>）

- アプリのデータ：`gomiappV3.1/data/<県>/<自治体>/`
- 元データ：`元データ/<県コード>_<県名>/<コード>_<名前>/`
- 問い合わせ：<課の名前> <電話>

## 収集日
（使った資料と URL、読み取り方、毎年やること）

## 品目
（使った資料、件数、手で足したもの）

## 今いる場所から探す
（町名と地区の対応のしかた）

## 確かめたこと
- 自動チェック：直す 0・注意 <n>（<日付>）
- 収集日：<地区>の 4/○・8/○・12/○・1/○・3/○ を市のカレンダーと見くらべて合っていた …
- 品目：<品目>…の区分が市の一覧と合っていた
- 町名を直したもの：<元の書き方> → <正式な町名>（理由）

## 人がやること
- [ ] <エージェントではできなかったこと・決めてほしいこと>（例：画像の文字が読めないページ、市への問い合わせ、スマホでの確認）
```

### 「人がやること」になりやすいもの

- 市への問い合わせ（商用利用の許可、資料の食いちがい）
- 資料がネットにない・ログインや画像認証（CAPTCHA）が必要
- 画像が荒く、書き写しても自信がない部分
- 決まりにない判断（例：地区の分け方が資料ごとにちがう）
- スマホのアプリでの最終確認、Push（公開）

## 6. 毎年の更新

新しい年度の資料が出たら（ふつう2〜3月）、`download_sources.py` → `update_year.py` → `check_muni.py` → `status.py`。
曜日で決まる市は、年末年始の日程（10〜11月ごろ発表）だけを `calendar.py` の `YEAR_END` に足す。
